# A.10 · Página 404 personalizada con recuperación

Fecha de revisión: 2026-08-28
Idea original: sustituir una 404 vacía por una página que explique el error y sugiera contenido relacionado/buscador.

## Veredicto

**ALREADY_COVERED COMPLETELY. NO REDISEÑAR POR ESTA IDEA.**

La web ya tiene una `404.html` personalizada, integrada con el shell V1, con `noindex,follow`, mensaje claro y múltiples rutas de recuperación. Además el sistema de QA ya verifica que el servidor devuelva un **HTTP 404 real**, evitando el problema de soft 404.

## Fuente primaria

Google Search Central · Troubleshoot crawling errors / 404
https://developers.google.com/search/docs/crawling-indexing/troubleshoot-crawling-errors

Google recomienda que una buena página 404:

- explique claramente que la página no existe;
- mantenga el look & feel/navegación del sitio;
- ofrezca links a páginas populares o Home;
- opcionalmente facilite informar del enlace roto;
- **devuelva HTTP 404**, no 200 con apariencia de error, para evitar soft 404.

También recomienda `410` cuando un recurso se elimina permanentemente y no existe reemplazo, aunque `404` es perfectamente válido.

## Qué está especialmente bien

### 1. No redirige a Home

Una redirección automática de cualquier URL inexistente a `/` sería mala UX y podría producir soft-404/confusión. La página actual conserva la URL fallida y explica el error.

### 2. No se indexa

`noindex,follow` es adecuado para la plantilla de error. Más importante aún es el status HTTP real.

### 3. Ofrece salidas relevantes

No intenta adivinar agresivamente qué quería el visitante: presenta destinos principales estables.

### 4. Coincide con el sistema visual/navegación actual

Evita la clásica 404 legacy que parece otro sitio.

## Única mejora opcional que podría estudiarse

**Reporte de enlace roto**, solo si existe un canal útil y no añade fricción/PII.

Ejemplo sencillo sin backend nuevo:

```html
<a href="mailto:davidportodiaz@gmail.com?subject=Enlace%20roto%20en%20davidportodiaz.com">
  Avisar de este enlace roto
</a>
```

Pero no lo considero necesario para cerrar A.10. También podría causar más ruido/spam que valor.

Otra opción futura, si Pagefind está disponible en producción y la experiencia ya está estable, sería mostrar un campo de búsqueda. Pero **no añadir búsqueda solo porque una checklist de 404 lo sugiera**: la página actual ya recupera bien al usuario y el asistente/Explore existen.

## Contrato que debe preservarse

1. URL inexistente → status 404.
2. Body útil `404.html`.
3. `noindex` presente.
4. sin canonical que apunte a Home.
5. sin redirect automático a Home.
6. shell/navegación funcionales.
7. links de recuperación sin roturas.
8. usable sin JS.
9. reflow/accesibilidad bajo los gates globales.

## Test recomendado

Si no está ya centralizado, mantener algo equivalente a:

```js
const response = await page.goto(`${origin}/__ruta-que-no-existe__`);
assert.equal(response.status(), 404);
assert.match(await page.title(), /Página no encontrada/);
assert.equal(await page.locator('meta[name="robots"]').getAttribute('content'), 'noindex,follow');
await expect(page.locator('a[href="/"]')).toBeVisible();
```

Y un smoke HTTP de producción que compruebe una ruta inexistente controlada.

No necesita un test SEO separado si `global-discoverability-browser` ya cubre exactamente estos invariantes.

## Qué NO hacer

- responder 200 para una página inexistente;
- redirigir todos los 404 a Home;
- canonicalizar la 404 a `/`;
- añadir contenido SEO/keywords a la página de error;
- mostrar recomendaciones personalizadas mediante tracking solo para la 404;
- cargar un servicio de búsqueda pesado para resolver un problema que ya está resuelto;
- crear múltiples plantillas 404 por sección;
- indexar la 404.

## Coste / beneficio

Implementación nueva: **no necesaria**.
Contrato actual: alto valor y ya existe.
Mejoras opcionales: bajo retorno hasta que exista evidencia de usuarios abandonando la 404.
