# D.4 · Guardado de posición / lista personal «leer después»

Fecha de reconstrucción: 2026-08-29  
Fuente histórica: PR #135, snapshot `8e72321d047c0445c5ac411ebe242af8a0386929`.  
Estado histórico final: `CONDITIONAL`.  
Revalidación actual: no se ha localizado una implementación personal de read-later/localStorage; `data/reading-list.json` es una lista editorial distinta y no satisface D.4.

## 1. Hipótesis original

Permitir guardar artículos/recomendaciones para leer después mediante `localStorage`, sin cuenta ni backend.

La ventaja propuesta era reducir fricción para visitantes recurrentes sin introducir autenticación.

## 2. Evolución en #135

### Revisión → `CONDITIONAL`

#135 considera técnicamente viable el patrón, pero señala coste de estado/gestión y exige recurrencia suficiente antes de pilotarlo.

### Matriz → `DEFERIR`

La matriz rebaja su prioridad:

> «Read-later local puede aportar pero no está entre principales fricciones observadas.»

### Autoridad final → `CONDITIONAL`

El cierre conserva posibilidad futura:

> «Read-later local solo si aparece demanda; no es una fricción prioritaria hoy.»

### Revalidación independiente

D.1–D.12 se mantienen sin elevar D.4.

## 3. No confundir con `data/reading-list.json`

El repo actual contiene `data/reading-list.json`, pero ese fichero modela una lista editorial de libros/lecturas con campos como `title`, `author`, `note`, `status` y `publish`.

No es:

- estado de un visitante;
- favoritos personales;
- posición de lectura;
- lista guardada en navegador.

Por tanto no sirve como evidencia de que D.4 esté implementada.

## 4. Qué problema debe demostrarse

Antes de crear estado local debe existir señal de que lectores quieren volver a piezas específicas y hoy pierden ese contexto.

Evidencia razonable:

- preguntas/research de usuarios;
- recurrencia suficiente en Cuaderno;
- lista creciente de contenido donde guardar tenga sentido;
- feedback explícito;
- journey donde favoritos reduzcan pasos reales.

No basta que «Pocket/Medium lo hacen».

## 5. Alcance mínimo si se reabre

La versión más simple sería guardar **URLs canónicas**, no copias de contenido:

```json
{
  "schemaVersion": 1,
  "items": [
    {
      "url": "/cuaderno/.../",
      "savedAt": "2026-09-01T12:00:00Z"
    }
  ]
}
```

La página resuelve título/metadata desde el DOM/índice actual cuando sea posible.

Evitar almacenar contenido editorial completo en localStorage.

## 6. Posición de lectura ≠ leer después

La idea original mezcla dos necesidades posibles:

- guardar una URL para volver;
- recordar una posición concreta de scroll.

No deben implementarse juntas automáticamente.

Recordar scroll añade edge cases:

- artículo cambiado;
- imágenes que alteran altura;
- deep links/hash;
- restauración inesperada;
- back/forward del navegador;
- varios dispositivos sin sincronización.

Empezar por «guardar URL» si la demanda real es esa. Añadir posición solo con necesidad demostrada.

## 7. Privacidad

`localStorage` evita backend pero sigue siendo almacenamiento persistente en dispositivo.

Contrato mínimo:

- datos no sensibles;
- solo URLs/IDs propios;
- botón claro para quitar/borrar;
- no almacenar manuscritos, emails o perfiles;
- no enviar la lista a analytics;
- documentar el comportamiento si llega a producción.

La preferencia local no debe convertirse en fingerprinting ni tracking cross-site.

## 8. Robustez ante cambios de URL

Si se guarda URL canónica:

- usar rutas canónicas actuales;
- al cargar lista, tolerar 404/retired content;
- ofrecer eliminar entradas rotas;
- si existe redirect oficial inequívoco, actualizar localmente;
- no mantener una segunda tabla manual de redirects dentro de D.4.

## 9. No-JS y progresive enhancement

La lectura esencial debe seguir disponible sin JS. Read-later puede ser mejora progresiva.

No esconder enlaces/contenido detrás de la función.

## 10. Accesibilidad

Si existe un control «Guardar»:

- nombre accesible inequívoco;
- estado perceptible (`Guardar` ↔ `Guardado`);
- no depender solo de icono/estrella/color;
- teclado;
- foco estable;
- feedback sin anuncios duplicados.

D.1 puede proporcionar confirmación, pero no justifica por sí misma construir D.4.

## 11. Estado vacío

Si se crea una lista, D.11 gobernará el empty state. No mostrar una pantalla muerta; explicar cómo guardar y ofrecer rutas útiles.

## 12. PWA/offline

L.2 ya cubre páginas visitadas offline mediante Service Worker. D.4 no debe duplicar caching ni prometer «guardado offline» si solo guarda URLs.

Diferencia:

```text
read-later = recordar qué quiero leer
PWA PAGE_CACHE = disponibilidad offline de páginas visitadas
```

## 13. Qué NO hacer

- cuenta/login solo para favoritos;
- backend de perfiles;
- sincronización multi-dispositivo sin demanda;
- almacenar artículos completos en localStorage;
- guardar posición automáticamente en cada scroll;
- convertir la lista en tracking;
- llamar «offline» a una URL guardada;
- confundir `data/reading-list.json` editorial con usuario;
- añadir badges/notificaciones para forzar regreso.

## 14. Trigger de reapertura

```text
repeated reader need
AND sufficient recurring content
AND local-only scope solves it
AND clear deletion/control
AND no conflict with browser/PWA behavior
```
