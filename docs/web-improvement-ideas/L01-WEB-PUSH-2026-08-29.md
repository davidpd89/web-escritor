# L.1 · Web Push opt-in

Fecha de reconstrucción: 2026-08-29  
Fuente histórica primaria: PR #135, snapshot `8e72321d047c0445c5ac411ebe242af8a0386929`.  
Estado histórico final: `REJECT`.

## Veredicto

#135 terminó rechazando Web Push para el proyecto actual. La razón no es incompatibilidad técnica: es falta de una necesidad temporal suficientemente fuerte para justificar permisos, subscriptions, endpoint/backend, mantenimiento, privacidad y fatiga de notificaciones cuando newsletter/RSS ya cubren novedades voluntarias.

## Hipótesis original

Aprovechar que el sitio ya dispone de PWA/manifest para ofrecer notificaciones opt-in de nuevos artículos o capítulos.

## Revalidación oficial actual

MDN mantiene Push API como ampliamente disponible, pero su arquitectura confirma el coste real:

- requiere service worker activo;
- `PushManager.subscribe()` crea una `PushSubscription`;
- la suscripción contiene endpoint y claves necesarias para entregar mensajes;
- el endpoint es una capability URL sensible;
- el service worker recibe el `push` y normalmente muestra una notificación.

Fuente: https://developer.mozilla.org/en-US/docs/Web/API/Push_API

La guía PWA de MDN también advierte que una notificación interrumpe al usuario y que Push debe reservarse para situaciones donde realmente no se puede esperar hasta la próxima visita.

Fuente: https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Offline_and_background_operation

Esto refuerza #135: soporte técnico no equivale a encaje de producto.

## Estado actual de `main`

`service-worker.js` ya existe y está dedicado a offline/cache:

- shell mínimo;
- navegación `networkFirstPage()`;
- assets stale-while-revalidate;
- exclusión explícita de media/Range;
- APIs no se cachean.

No debe contaminarse esta autoridad con Push solo porque ya haya SW.

No se ha demostrado actualmente:

- backend de suscripciones;
- VAPID/send pipeline;
- modelo de topic/preferences;
- política de retención de endpoints;
- gestión de expiración/`pushsubscriptionchange`;
- calendario editorial que necesite alertas inmediatas.

## Por qué newsletter/RSS ganan hoy

Para las necesidades actuales:

- newsletter = consentimiento explícito + relación editorial;
- RSS = canal pull sin permiso de navegador;
- página/eventos = fuente canónica para fechas;
- social/Metricool = distribución externa.

Añadir Push crearía un quinto canal con nuevas obligaciones sin una tarea que los anteriores no puedan resolver.

## Trigger extremadamente estricto de reapertura

Solo reabrir si aparece una necesidad temporal real, por ejemplo:

- contenido/actividad que pierde utilidad si el usuario no se entera pronto;
- usuarios piden explícitamente notificaciones;
- frecuencia suficientemente baja y predecible;
- capacidad de segmentar para evitar ruido;
- ownership operativo del backend y bajas;
- política de retención y seguridad de endpoints.

Un nuevo artículo del Cuaderno, por sí solo, no supera el trigger.

## Arquitectura mínima si algún día se reabre

```text
explicit user action
→ permission request
→ PushSubscription
→ secure backend storage
→ topic/preference
→ send service
→ SW push handler
→ notification
→ unsubscribe/delete
→ subscription-change handling
```

No guardar endpoints en el repositorio ni exponerlos en logs.

## UX de permisos

Nunca pedir permiso:

- al cargar la Home;
- en la primera interacción genérica;
- mediante dark pattern;
- antes de explicar qué se notificará y con qué frecuencia.

La petición tendría que seguir una acción deliberada tipo «Avisarme de X».

## Relación con L.2

Tener un service worker para offline no hace que Push sea «gratis». Son capacidades diferentes con estados, privacidad y operaciones distintas.

## Relación con H/email

Newsletter debe estabilizar sus journeys E2E antes de añadir otro canal de notificación. H.1/H.2 ya tienen deuda operativa propia.

## Relación con L.4

No implementar badges como sustituto silencioso de Push. L.4 también fue rechazada y además necesita un modelo de estado «no leído» que hoy no existe.

## Qué NO hacer

- prompt de permiso al entrar;
- SDK/proveedor push por checklist;
- reutilizar email como identidad push sin consentimiento específico;
- almacenar endpoint indefinidamente;
- notificar cada artículo;
- meter lógica Push en SW sin tests de cache/regresión;
- justificarlo por «engagement» sin hipótesis;
- considerar Brevo Push como razón para subir plan.

## Señales para medir un piloto futuro

Si llegara a aprobarse:

- opt-in rate tras explicación;
- deny rate;
- unsubscribe rate;
- delivery/click;
- conversiones útiles;
- frecuencia por usuario;
- errores de subscription;
- impacto de permisos/UX.

No medir éxito por número bruto de endpoints.

## Recomendación para Clara/Claude

**No implementar Web Push.** Mantener newsletter/RSS como canales voluntarios. Reabrir solo ante una necesidad temporal demostrada y una arquitectura operativa/privacidad completa.
