## Veredicto actual

`REJECT · PRODUCT_JOB_NOT_DEMONSTRATED · TECHNICAL_PREREQUISITES_PARTLY_EXIST · RSS_NOT_PRESENT · NO_PUSH_BACKEND`

La decisión sigue siendo no implementar Web Push ahora, pero la razón debe ser precisa: **en 2026 Web Push es técnicamente viable para este sitio; lo que no está demostrado es el trabajo de producto que justificaría añadir otro canal de notificación y su operación permanente**.

No se rechaza por compatibilidad ni porque falte una PWA. Se rechaza porque no existe hoy un caso en el que la información pierda suficiente valor si el lector la descubre más tarde, ni demanda observada que compense permisos, subscriptions, backend, seguridad de endpoints, lifecycle, bajas, segmentación, observabilidad y riesgo de fatiga.

## 1. Correcciones frente a la formulación anterior

### Compatibilidad

La compatibilidad ya no es una objeción razonable:

- MDN clasifica Push API como ampliamente disponible y señala disponibilidad transversal desde marzo de 2023;
- Apple documenta Web Push para Home Screen web apps en iOS/iPadOS 16.4 o posterior y para Safari en macOS;
- Apple exige que la solicitud de permiso derive de un gesto explícito del usuario.

Fuentes oficiales revalidadas el 2026-08-30:

- https://developer.mozilla.org/en-US/docs/Web/API/Push_API
- https://developer.mozilla.org/en-US/docs/Web/API/PushSubscription/endpoint
- https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers

### RSS

La versión anterior decía que «newsletter/RSS» ya cubrían las novedades. La inspección del `main` actual no localiza un feed RSS/Atom ni referencias `rss` en el índice de código auditado. Por tanto:

```text
RSS = posible alternativa futura de distribución pull
RSS != canal existente demostrado en main
```

No utilizar una capacidad inexistente como argumento para rechazar otra.

### Newsletter

Newsletter sí existe y sigue siendo un canal editorial más próximo al caso de uso que Push. Sin embargo, tampoco debe presentarse como completamente cerrado: #206 mantiene documentado el crossfinding entre copy de privacidad, markup y comportamiento real de consentimiento/DOI. La comparación correcta es «canal existente que debe estabilizarse», no «sustituto perfecto ya resuelto».

## 2. Estado técnico real de `main`

### Manifest

`manifest.json` ya declara:

```json
"display": "standalone"
```

Esto encaja con el modo de aplicación web que Apple utiliza para Web Push en Home Screen en iOS/iPadOS.

### Service Worker

`service-worker.js` es una autoridad deliberadamente pequeña de offline/cache:

- precache de shell mínimo;
- navegación network-first;
- CSS/JS network-first;
- assets stale-while-revalidate;
- APIs excluidas del cache owner;
- media y Range excluidos del flujo genérico;
- limpieza explícita de caches legacy.

No contiene:

- `PushManager`;
- `push`;
- `notificationclick`;
- `pushsubscriptionchange`;
- VAPID;
- send pipeline;
- persistencia de `PushSubscription`;
- endpoint de alta/baja;
- preferencias/topics;
- observabilidad de entrega.

Tener Service Worker reduce una precondición, pero **no convierte Push en una extensión trivial del cache**.

## 3. Coste y superficie real de Web Push

MDN documenta que cada `PushSubscription` contiene endpoint y claves necesarias para el envío. El endpoint es una capability URL y debe tratarse como información sensible. Apple exige registrar endpoint y claves en el servidor y disponer de servidor capaz de enviar los mensajes mediante el estándar Web Push/VAPID.

Una implementación completa necesita como mínimo:

```text
explicación del valor
→ gesto explícito del usuario
→ permission request
→ PushManager.subscribe()
→ envío seguro de subscription al backend
→ almacenamiento + retención
→ preferencia/topic
→ VAPID/send service
→ handler `push`
→ notificación visible
→ navegación `notificationclick`
→ unsubscribe/delete
→ lifecycle / subscriptions inválidas
→ observabilidad y limpieza
```

No almacenar endpoints en el repositorio, analytics o logs no gobernados.

## 4. Job de producto que falta

Web Push tiene valor cuando **la latencia importa**. La propia documentación de Apple lo enmarca en eventos importantes y sensibles al tiempo.

Ejemplos que podrían justificar un piloto futuro:

- «avísame cuando se abra una reserva/plaza concreta»;
- «avísame el día exacto en que este libro pase a estar disponible»;
- «avísame cuando se publique el siguiente capítulo de esta serie» si lectores han pedido explícitamente ese comportamiento y la cadencia lo hace útil;
- evento o directo con ventana temporal estrecha.

No lo justifican por sí solos:

- cada nuevo artículo del Cuaderno;
- recordatorios promocionales genéricos;
- aumentar engagement;
- tener ya PWA/manifest;
- la existencia de un SDK/proveedor;
- replicar automáticamente cada newsletter.

## 5. Trigger de reapertura

Reabrir L.1 solo cuando estén documentados simultáneamente:

1. **evento/job concreto** que pierda valor con retraso;
2. **demanda observada** de ese tipo de aviso;
3. **frecuencia esperada** y límite por usuario;
4. **segmentación/preferencia explícita** para no convertirlo en broadcast genérico;
5. **owner editorial** de qué se envía y cuándo;
6. **owner técnico** de subscriptions/send/lifecycle;
7. **retención y borrado** de endpoints/keys;
8. **threat model** y protección CSRF/XSRF del alta, recomendada también por MDN;
9. **unsubscribe/revoke path** comprobado;
10. **métrica de éxito** vinculada al job, no al número de endpoints.

Sin esas diez piezas, el estado permanece `REJECT`.

## 6. UX de permisos

Si algún día se reabre:

- nunca pedir permiso al cargar la Home;
- nunca pedirlo después de una interacción no relacionada;
- explicar primero qué se notificará;
- usar un CTA contextual como «Avisarme de X»;
- llamar a la suscripción desde el gesto deliberado, como exige Apple;
- respetar `denied` sin insistencia ni dark patterns;
- proporcionar una vía clara para dejar de recibir avisos.

Safari exige además que los pushes recibidos se presenten al usuario; no diseñar silent push como mecanismo de background sync.

## 7. Alternativas actuales por necesidad

| Necesidad | Canal actual / preferido | Observación |
|---|---|---|
| Relación editorial periódica | Newsletter | Existe; estabilizar #206 antes de añadir otro journey sensible. |
| Descubrir contenido cuando el lector quiera | Web/Cuaderno | Ya es la autoridad pública. |
| Distribución pull interoperable | RSS/Atom | No existe en el `main` auditado; sería una idea separada y de menor superficie que Push. |
| Difusión externa | Canales sociales/distribución existente | No requiere permiso de navegador ni almacenar subscriptions aquí. |
| Aviso realmente temporal y solicitado | Web Push | Solo si aparece el job y supera el trigger. |

La comparación evita afirmar que todos los canales son equivalentes: Push resuelve un problema distinto, pero ese problema todavía no está demostrado.

## 8. Relación con el Service Worker

No mezclar de forma oportunista la autoridad offline con Push.

Si L.1 se reabre, cualquier cambio en `service-worker.js` debe preservar y ampliar el QA existente de cache/offline. Como mínimo deben probarse:

- install/activate actuales;
- navegación offline;
- exclusiones API/media/Range;
- recepción de `push`;
- notificación visible;
- click/navigation;
- subscription invalidation/change;
- ausencia de regresión de cache.

No crear un segundo Service Worker ni un runtime paralelo.

## 9. Métricas de un piloto futuro

Solo si el trigger se supera:

- tasa de opt-in después de explicación;
- `denied` rate;
- unsubscribe/revoke rate;
- delivery/error por tipo de subscription;
- CTR sobre el evento específico;
- conversión o utilidad del job concreto;
- frecuencia real por usuario;
- endpoints inválidos eliminados;
- impacto sobre newsletter/otros canales.

No utilizar número bruto de subscriptions como métrica principal.

## 10. Qué no hacer

- no prompt de permiso al entrar;
- no Push porque «ya hay PWA»;
- no SDK/proveedor por checklist;
- no copiar todas las newsletters a Push;
- no notificar cada artículo automáticamente;
- no vincular Push a email sin consentimiento/propósito específico;
- no conservar endpoints indefinidamente;
- no loguear subscription completa;
- no añadir lógica al SW sin tests de regresión;
- no presentar RSS como existente hasta que realmente se implemente;
- no usar engagement abstracto como business case.

## 12. Cierre

L.1 continúa `REJECT`, pero con una justificación más sólida y actual: **el sitio tiene parte de los prerrequisitos técnicos y los navegadores modernos soportan Web Push; falta el caso de producto que compense crear y mantener la operación**.

La decisión debe cambiar solo si aparece un aviso temporal concreto, solicitado y medible. Hasta entonces, conservar el Service Worker enfocado a offline/cache es mejor arquitectura que ampliar su responsabilidad por disponibilidad técnica.
