## Veredicto actual

`REJECT · PRODUCT_JOB_NOT_DEMONSTRATED · TECHNICAL_PREREQUISITES_PARTLY_EXIST · RSS_ALREADY_COVERED · NO_PUSH_BACKEND`

La decisión sigue siendo no implementar Web Push ahora. En 2026 Web Push es técnicamente viable para este sitio; lo que no está demostrado es un trabajo de producto sensible al tiempo que justifique añadir otro canal de notificación y su operación permanente.

No se rechaza por compatibilidad, por ausencia de PWA ni por falta de canales de distribución. Se rechaza porque no existe hoy un caso en el que la información pierda suficiente valor si el lector la descubre más tarde ni demanda observada que compense permisos, subscriptions, backend, seguridad de endpoints, lifecycle, bajas, segmentación, observabilidad y riesgo de fatiga.

## 1. Revalidación de compatibilidad

La compatibilidad ya no es una objeción razonable:

- MDN clasifica Push API como ampliamente disponible;
- Apple documenta Web Push para Home Screen web apps en iOS/iPadOS 16.4 o posterior y Safari en macOS;
- Apple exige que la solicitud de permiso derive de un gesto explícito del usuario.

Fuentes oficiales revalidadas el 2026-08-30:

- https://developer.mozilla.org/en-US/docs/Web/API/Push_API
- https://developer.mozilla.org/en-US/docs/Web/API/PushSubscription/endpoint
- https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers

## 2. Corrección de revalidación · RSS sí existe

Una búsqueda inicial de repositorio no devolvió el feed y llevó a clasificar RSS erróneamente como ausente. La comprobación directa posterior de O.1 corrige esa conclusión.

`main` contiene:

- `scripts/build-feed.py`;
- `cuaderno/feed.xml` en RSS 2.0;
- `assets/rss.xsl`;
- autodiscovery en `/cuaderno/` mediante `<link rel="alternate" type="application/rss+xml" ...>`;
- enlace visible `RSS del Cuaderno` en el footer;
- modo `python scripts/build-feed.py --check`;
- exclusión de `noindex` y `CollectionPage`;
- output determinista y máximo de 50 entradas.

Por tanto:

```text
RSS = canal pull existente y gobernado
RSS != sustituto funcional de un aviso temporal solicitado
```

La existencia de RSS reduce aún más la necesidad de Push para simples novedades editoriales, pero **no** debe utilizarse como argumento para afirmar que ambos canales resuelven exactamente el mismo problema.

## 3. Newsletter

Newsletter también existe y es un canal editorial más próximo al caso de uso general de novedades. Sin embargo, #206 mantiene documentado el crossfinding entre copy de privacidad, markup y comportamiento real de consentimiento/DOI. Debe estabilizarse ese journey antes de añadir otro canal sensible.

## 4. Estado técnico real de `main`

### Manifest

`manifest.json` declara `"display": "standalone"`, compatible con el modelo Home Screen usado por Apple para Web Push en iOS/iPadOS.

### Service Worker

`service-worker.js` es una autoridad deliberadamente pequeña de offline/cache:

- precache de shell mínimo;
- navegación network-first;
- CSS/JS network-first;
- assets stale-while-revalidate;
- APIs excluidas del cache owner;
- media y Range excluidos del flujo genérico;
- limpieza explícita de caches legacy.

No contiene:

- `PushManager`;
- handler `push`;
- `notificationclick`;
- `pushsubscriptionchange`;
- VAPID;
- send pipeline;
- persistencia de `PushSubscription`;
- endpoint de alta/baja;
- preferencias/topics;
- observabilidad de entrega.

Tener Service Worker reduce una precondición, pero no convierte Push en una extensión trivial del cache.

## 5. Coste y superficie de Web Push

MDN documenta que cada `PushSubscription` contiene endpoint y claves necesarias para el envío. El endpoint es una capability URL y debe tratarse como información sensible. Una implementación completa necesita al menos:

```text
explicación del valor
→ gesto explícito
→ permission request
→ PushManager.subscribe()
→ envío seguro al backend
→ almacenamiento + retención
→ preferencia/topic
→ VAPID/send service
→ handler push
→ notificación visible
→ notificationclick
→ unsubscribe/delete
→ lifecycle de subscriptions inválidas
→ observabilidad y limpieza
```

No almacenar endpoints en el repositorio, analytics o logs no gobernados.

## 6. Job de producto que falta

Web Push aporta valor cuando **la latencia importa**.

Podrían justificar un piloto futuro:

- «avísame cuando se abra una reserva/plaza concreta»;
- «avísame el día exacto en que este libro pase a estar disponible»;
- «avísame cuando se publique el siguiente capítulo de esta serie» si existe demanda explícita y cadencia útil;
- evento o directo con ventana temporal estrecha.

No lo justifican por sí solos:

- cada nuevo artículo del Cuaderno;
- replicar RSS;
- replicar automáticamente newsletter;
- recordatorios promocionales genéricos;
- “aumentar engagement”;
- tener ya manifest/PWA;
- disponer de un SDK/proveedor.

## 7. Trigger de reapertura

Reabrir L.1 solo cuando estén documentados simultáneamente:

1. evento/job concreto que pierda valor con retraso;
2. demanda observada de ese aviso;
3. frecuencia esperada y límite por usuario;
4. segmentación/preferencia explícita;
5. owner editorial;
6. owner técnico de subscriptions/send/lifecycle;
7. retención y borrado de endpoints/keys;
8. threat model y protección del alta;
9. unsubscribe/revoke path comprobado;
10. métrica de éxito ligada al job, no al número de endpoints.

Sin esas diez piezas, el estado permanece `REJECT`.

## 8. UX de permisos

Si algún día se reabre:

- nunca pedir permiso al cargar la Home;
- nunca pedirlo tras una interacción no relacionada;
- explicar primero qué se notificará;
- usar CTA contextual como «Avisarme de X»;
- llamar a la suscripción desde un gesto deliberado;
- respetar `denied` sin insistencia ni dark patterns;
- proporcionar una vía clara de baja.

No diseñar silent push como mecanismo de background sync.

## 9. Alternativas actuales por necesidad

| Necesidad | Canal actual / preferido | Observación |
|---|---|---|
| Relación editorial periódica | Newsletter | Existe; estabilizar #206. |
| Descubrir contenido cuando el lector quiera | Web/Cuaderno | Autoridad pública. |
| Distribución pull interoperable | RSS del Cuaderno | Ya existe, es visible y tiene builder/check. |
| Difusión externa | Canales sociales/distribución existente | No requiere permiso de navegador ni subscriptions aquí. |
| Aviso realmente temporal y solicitado | Web Push | Solo si aparece el job y supera el trigger. |

Push resuelve un problema distinto, pero ese problema todavía no está demostrado.

## 10. Relación con el Service Worker y QA

No mezclar de forma oportunista la autoridad offline con Push. Si L.1 se reabre, cualquier cambio en `service-worker.js` debe preservar el QA PWA existente y probar adicionalmente:

- recepción de `push`;
- notificación visible;
- click/navigation;
- invalidación/cambio de subscription;
- ausencia de regresión en cache/offline.

No crear un segundo Service Worker ni runtime paralelo.

## 11. Métricas de un piloto futuro

Solo si el trigger se supera:

- opt-in después de explicación;
- `denied` rate;
- unsubscribe/revoke rate;
- delivery/error por tipo de subscription;
- CTR sobre el evento específico;
- utilidad/conversión del job;
- frecuencia real por usuario;
- endpoints inválidos eliminados;
- impacto sobre newsletter/RSS/otros canales.

No usar número bruto de subscriptions como métrica principal.

## 12. Qué no hacer

- no prompt al entrar;
- no Push porque «ya hay PWA»;
- no SDK/proveedor por checklist;
- no copiar todas las newsletters a Push;
- no notificar cada artículo automáticamente;
- no duplicar RSS con Push sin job temporal;
- no vincular Push a email sin propósito específico;
- no conservar endpoints indefinidamente;
- no loguear subscriptions completas;
- no añadir lógica al SW sin tests de regresión;
- no volver a negar la existencia de `/cuaderno/feed.xml` sin inspección directa;
- no usar engagement abstracto como business case.

## 13. Trazabilidad de la corrección RSS

La revalidación directa de O.1 confirma en el mismo `main` auditado:

```text
scripts/build-feed.py
cuaderno/feed.xml
cuaderno/index.html -> rel=alternate application/rss+xml
footer -> RSS del Cuaderno
```

Esta evidencia prevalece sobre la búsqueda textual inicial que no devolvió resultados.

## 14. Cierre

L.1 continúa `REJECT`, pero con la justificación correcta: **el sitio tiene PWA, Service Worker, newsletter y RSS; los navegadores modernos soportan Web Push; falta un caso temporal, solicitado y medible que compense crear y mantener la operación Push**.

Hasta que aparezca ese caso, conservar el Service Worker enfocado a offline/cache y utilizar los canales existentes es mejor arquitectura.
