# E.2 — Auditoría de INP e interacciones lentas

Fecha de reconstrucción: 2026-08-29  
Fuente histórica primaria: PR #135, snapshot `8e72321d047c0445c5ac411ebe242af8a0386929`  
Estado efectivo: **`IMPLEMENT_AFTER_CURRENT_DEBT`**

## 1. Propósito

E.2 nació como una auditoría específica de Interaction to Next Paint (INP), especialmente sobre scripts, popups, modales y componentes interactivos. Durante #135 la idea se refinó para evitar dos errores:

1. tratar todo JavaScript como culpable sin medir;
2. convertir un threshold de laboratorio en sustituto de datos reales de campo.

Esta PR reconstruye esa investigación completa. No modifica runtime ni instala RUM.

## 2. Veredicto

**`IMPLEMENT_AFTER_CURRENT_DEBT`**.

La necesidad es real porque INP es un Core Web Vital de interactividad y el sitio contiene cada vez más journeys dinámicos. Pero la acción correcta es **diagnóstico por interacción y contributor**, no “optimizar `script.js`” de forma genérica.

#135 estableció una secuencia:

```text
lab reproducible
→ interacción problemática
→ contributor real
→ fix mínimo
→ comparación before/after
→ field data cuando exista muestra suficiente
```

## 3. Hipótesis original

La lista original proponía auditar INP porque:

- INP sustituyó a FID como métrica de interactividad;
- scripts monolíticos y modales podían introducir trabajo largo;
- existían pendientes previos sobre componentes pesados.

La formulación inicial asumía que los grandes scripts eran un sospechoso probable, no una causa demostrada.

## 5. Fuentes primarias recuperadas

#135 sustituyó referencias genéricas por fuentes oficiales:

- web.dev — INP;
- web.dev — Optimize INP;
- Chrome UX Report API;
- CrUX History API;
- Chrome Long Animation Frames API en una pasada posterior;
- MDN Prioritized Task Scheduling / `scheduler.yield()` como técnica condicional.

La lectura correcta fue que INP requiere observar el tiempo desde la interacción hasta el siguiente paint y localizar qué bloquea ese resultado.

## 6. Qué no demuestra Lighthouse por sí solo

Una ejecución Lighthouse puede detectar problemas o dar señal de laboratorio, pero no sustituye:

- interacciones concretas de usuario;
- dispositivos reales;
- distribución P75 de campo;
- variación por navegador;
- journeys que no se ejecutan durante la auditoría automática.

Por eso #135 separó `LAB_VERIFIED` de field data.

## 7. Problema de muestra de campo

En las pasadas finales de #135 se registró que Search Console/CrUX todavía no tenían muestra suficiente para el dominio.

Eso produjo dos decisiones complementarias:

1. E.2 no debe esperar pasivamente para siempre: usar interacción/trace de laboratorio ahora;
2. R.61 elevó un posible piloto de Cloudflare Web Analytics como RUM temporal mientras CrUX carezca de muestra, pero esa es una operación separada con CSP/privacidad/third-party contract.

No fusionar E.2 con R.61.

## 8. R.12 — Long Animation Frames

La quinta pasada añadió una extensión concreta:

> Long Animation Frames y `scheduler.yield()` pueden ayudar a diagnosticar/refactorizar interacciones pesadas, pero solo después de reproducir un problema.

LoAF puede exponer frames largos y contributors. `scheduler.yield()` puede dividir trabajo, pero no debe añadirse como dependencia funcional universal.

#135 fue explícita:

- primero optimizar algoritmo;
- luego reducir DOM writes/parseos/regex repetidas;
- solo si queda trabajo inherentemente divisible, probar yield/chunking;
- mantener fallback para navegadores sin esa API.

## 9. Herramientas especialmente relevantes

La pasada R.12 señaló herramientas de escritura que procesan texto localmente. Ese diseño protege privacidad, pero puede crear CPU work grande.

Fixtures sintéticos sugeridos:

- 10k palabras;
- 50k palabras;
- 100k cuando la herramienta lo soporte.

No utilizar manuscritos reales del usuario para benchmarks versionados.

## 10. Journeys que debería cubrir una futura auditoría

### Shell

- abrir/cerrar Explorar;
- abrir asistente;
- búsqueda;
- cierre y retorno de foco.

### Formularios

- validación;
- submit;
- estado pending/error/success.

### Herramientas

- pegar/cargar fixture grande;
- ejecutar análisis;
- renderizar resultados;
- cambiar filtros si existen.

### Contenido

- scroll en artículos largos;
- reading progress cuando está montado;
- interacción con accordions/tabs/quiz reales.

### PWA

- instalación/acciones relevantes solo si intervienen en main thread.

## 11. Métricas de laboratorio útiles

No reducir la auditoría a un único número.

Registrar por interacción:

```text
input delay
processing duration
presentation delay
total interaction latency
long tasks / LoAF
DOM/render contributors
visible-result timestamp
errors
```

Y guardar suficiente contexto para reproducir el caso.

## 12. Priorización

Orden recomendado:

```text
interacción principal bloqueada
> typing/click frecuente con latencia perceptible
> herramienta CPU-heavy
> interacción secundaria ocasional
> microanimación sin impacto funcional
```

## 13. No hacer

- minificar/repartir bundles solo porque “INP”;
- añadir Web Worker a cada herramienta;
- meter `scheduler.yield()` en cada loop;
- instrumentar texto del usuario;
- enviar manuscritos o eventos sensibles a terceros;
- usar un threshold flakey de CI como única verdad;
- culpar a `script.js` por tamaño sin trace;
- eliminar funciones correctas para bajar una métrica sintética;
- declarar `VERIFIED_E2E` por un Lighthouse verde.

## 14. Posible harness de auditoría

La investigación de #135 sugiere que el repo ya tiene Playwright/QA reutilizable. Una implementación futura debería aprovechar esa infraestructura.

Conceptualmente:

```js
await page.goto(route);
// warmup
// start performance observers
await performInteraction();
const result = await collectInteractionDiagnostics();
```

El harness debe almacenar diagnóstico aunque un caso falle.

## 15. LoAF como diagnóstico progresivo

Solo en Chromium que lo soporte:

```js
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    // duration, blockingDuration, scripts...
  }
}).observe({ type: 'long-animation-frame', buffered: true });
```

No hacer que la prueba funcional dependa de LoAF: Firefox/WebKit deben seguir ejecutando el journey.

## 16. Web Worker

Comparar Worker cuando:

- el trabajo sea puro/CPU-heavy;
- el input sea suficientemente grande;
- serializar/copy no anule la mejora;
- exista un boundary claro.

No introducir Worker por patrón arquitectónico si un algoritmo más eficiente resuelve el problema.

## 17. Relación con E.5 performance budget

E.5 controla crecimiento estático de bytes/requests. E.2 mide latencia de interacción.

Un bundle pequeño puede tener un handler lento. Un bundle grande puede estar cacheado y no afectar la interacción concreta.

Necesitamos ambos contratos, sin confundirlos.

## 18. Relación con terceros

Scripts externos pueden contribuir a long tasks, pero E.8 es la autoridad del inventario de terceros. Si un contributor es GoatCounter/Metricool/Brevo/otro, la corrección debe respetar ese contrato y no introducir un segundo inventario.

## 19. Estado actual de `main`

La búsqueda actual no ha localizado una suite dedicada a INP/LoAF ni una implementación específica que cierre E.2.

Eso no significa que el repo carezca de QA de interacción: existen múltiples workflows browser y Lighthouse. Significa que **la pregunta específica de INP por interacción/contributor sigue abierta**.

No se cambia el estado a `ALREADY_COVERED`.

## 20. RUM futuro

Cuando CrUX tenga muestra suficiente, comparar P75 por familias relevantes. Antes de eso, un piloto de RUM solo merece existir si produce decisiones incrementales y cumple:

- third-party inventory;
- CSP mínima;
- privacidad factual;
- bytes/CPU medidos;
- retireWhen definido.

Esta PR no configura nada externo.

## 21. DoD de futura implementación

- muestra de journeys definida;
- fixtures sintéticos para herramientas pesadas;
- baseline before;
- diagnóstico por interacción;
- al menos un contributor reproducible antes de refactor;
- fix basado en contributor;
- before/after;
- equivalencia funcional cross-browser;
- ningún contenido sensible enviado;
- artifacts diagnósticos persistentes;
- CrUX/RUM tratado como capa de campo, no sustituto del lab.

## 25. Conclusión

E.2 conserva **`IMPLEMENT_AFTER_CURRENT_DEBT`**. El objetivo no es “tener una prueba de INP”, sino construir evidencia reproducible sobre interacciones reales, identificar contributors y corregir únicamente los que degradan la experiencia. Los datos de campo se añaden cuando haya muestra o mediante un piloto separado y justificado; nunca se inventan a partir de un Lighthouse aislado.
