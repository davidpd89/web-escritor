# B.7 · IndexNow post-deploy

Fecha de reconstrucción: 2026-08-29

Idea original: notificar a Bing/IndexNow cuando una URL pública se añade, cambia materialmente o se elimina, reduciendo la latencia de descubrimiento de cambios.

Fuente histórica principal: PR #135, snapshot `8e72321d047c0445c5ac411ebe242af8a0386929`.

Estado final: `IMPLEMENT_AFTER_CURRENT_DEBT`.

## Veredicto reconciliado

**IMPLEMENT_AFTER_CURRENT_DEBT. INDEXNOW SÍ APORTA, PERO SOLO POST-DEPLOY, PARA URLS PÚBLICAS MATERIALMENTE CAMBIADAS Y SIN CONFUNDIR “RECIBIDO” CON “INDEXADO”.**

B.7 acumuló varias capas importantes en #135: hipótesis original, plan de integración, blueprint de código, runbook de frescura/crawlers y una corrección tardía esencial sobre la key. Esta PR preserva toda esa evolución y marca explícitamente qué texto antiguo quedó superseded.

## 1. Hipótesis original

`docs/IDEAS-MEJORA-WEB-2026-08-27.md` propuso usar IndexNow para notificar publicaciones/cambios a Bing en vez de depender únicamente del rastreo periódico.

La hipótesis correcta no es “IndexNow posiciona más”, sino **reducir el tiempo durante el que buscadores/sistemas dependientes pueden seguir viendo una versión vieja**.

### 2.5 · Decimoquinta pasada R.85 → corrección de la key

`docs/IDEAS-MEJORA-WEB-DECIMOQUINTA-PASADA-2026-08-28.md` corrigió explícitamente la arquitectura:

**La key de IndexNow es material público de verificación de ownership, no un secreto convencional.**

El protocolo exige que pueda recuperarse, por ejemplo, en:

```text
https://davidportodiaz.com/{key}.txt
```

con la key como contenido, o una `keyLocation` pública compatible.

Por tanto, la frase anterior “la key real nunca commit / tratar como GitHub Secret” queda **SUPERSEDED por R.85**.

La corrección no significa imprimirla innecesariamente en logs. Significa que su modelo de seguridad es distinto: está diseñada para ser verificable públicamente.

## 3. Fuente primaria actual

IndexNow protocol:

- https://www.indexnow.org/documentation
- https://www.indexnow.org/faq

### Operaciones

Notificar URLs:

- añadidas;
- actualizadas;
- eliminadas.

### Límite

Hasta 10.000 URLs por POST. Para este sitio eso es un límite técnico, no una meta; enviar únicamente las URL realmente cambiadas.

### Endpoint general

```text
https://api.indexnow.org/indexnow
```

### Ownership

Key hexadecimal/UTF-8 según protocolo y fichero públicamente accesible en el host o `keyLocation` válida.

### Respuestas

- `200`: recibido;
- `202`: recibido, validación de key pendiente;
- `400`: request inválida;
- `403`: key no válida/no accesible;
- `422`: host/URL/key incoherente;
- `429`: demasiadas peticiones.

**200/202 no significan indexación, ranking ni citación.**

## 5. Arquitectura final recomendada

### 5.1 · Fuente de URLs

Preferir comparación entre **artefactos públicos** base/head o manifests de release.

Motivo: cambiar un builder/template/dato puede alterar muchas páginas aunque `git diff` solo muestre un script/JSON.

Flujo:

```text
public artifact base
+
public artifact head
→ hash/compare por URL pública
→ added / materially modified / deleted
→ filtro registry/indexability
```

Reutilizar `content-registry.json`, sitemap/manifest público y release tooling existente. No crear una segunda lista manual de URLs.

### 5.2 · Filtros obligatorios

Excluir:

- `noindex`;
- staging/preview;
- internal;
- gated/private;
- docs/tests/build artifacts;
- fragment-only;
- URLs que todavía no responden en producción;
- cambios de bytes que no alteran contenido público relevante si el sistema puede distinguirlos de forma fiable.

### 5.3 · Orden post-deploy

```text
1. build release
2. deploy
3. verify production exact release SHA
4. smoke canonical/indexability
5. derive changed public URLs
6. verify public IndexNow key file
7. POST IndexNow
8. record response
```

No invertir 3–7.

## 6. Script propuesto por #135

La implementación futura puede seguir el blueprint stdlib y evitar una Action externa innecesaria.

Responsabilidades:

- CLI `--dry-run`;
- leer lista de URLs desde artefacto/diff;
- host exacto `davidportodiaz.com`;
- HTTPS obligatorio;
- dedupe;
- <=10.000;
- construir payload `host`, `key`, `keyLocation`, `urlList`;
- timeout;
- manejo de status;
- salida legible sin imprimir material innecesario;
- retries limitados/backoff solo donde proceda.

No instalar una dependencia npm/Python si stdlib/curl cubre el protocolo.

## 7. Modelo correcto de la key

### Es pública por diseño

El fichero de verificación necesita ser accesible al servicio. No llamarla “secreto” en la arquitectura final.

### Aun así

- no reutilizar como credencial para otros servicios;
- no imprimirla repetidamente en logs;
- no mezclar con tokens privados;
- mantener rotación documentada;
- si rota: publicar nuevo fichero → verificar deploy → empezar submissions nuevas → retirar anterior cuando proceda.

## 8. Failure semantics

### IndexNow falla

No rollback del sitio por un 429/5xx del servicio. El release web puede estar correcto aunque la notificación falle.

Sí debe:

- quedar observabilidad;
- distinguir request inválida de servicio temporal;
- retry acotado cuando tenga sentido;
- permitir reejecución segura/dedupe.

### Key no verificable

`403/422` es fallo de configuración/ownership y requiere intervención; no martillear el endpoint.

## 9. Crawler Hints / Cloudflare

R.87 preservado:

- no activar proxy Cloudflare solo por Crawler Hints;
- con DNS-only, esa capacidad no justifica cambio de arquitectura;
- IndexNow directo no depende de Cloudflare proxy.

Si en otro proyecto/PR se decide proxificar por motivos propios, Crawler Hints puede reevaluarse como optimización separada, nunca como requisito de B.7.

## 10. Tests de implementación futura

### Unitarios

- URL HTTP rechazada;
- host extranjero rechazado;
- dedupe;
- >10.000 falla;
- vacío = no submit;
- noindex/internal excluido;
- payload correcto;
- keyLocation correcta;
- parsing 200/202/400/403/422/429;
- dry-run no hace red.

### Integración release

- job solo después de deploy/verify exact SHA;
- fixture de changed artifact produce lista esperada;
- página no publicada no se envía;
- eliminación pública sí puede notificarse;
- fallo IndexNow no marca falsamente deploy como revertido.

### Producción

- key file responde 200 con contenido esperado;
- una URL de prueba real/cambio legítimo puede recibir 200/202;
- registrar como `RECEIVED`/`PENDING`, nunca `INDEXED` sin evidencia de índice.

## 11. Qué NO hacer

- enviar todo el sitemap en cada deploy;
- enviar antes de producción;
- usar `git diff` como única fuente de verdad si builders afectan múltiples páginas;
- enviar noindex/staging/private;
- transformar un 200 en “Google/Bing ya indexó”;
- prometer ranking;
- activar Cloudflare proxy solo para esto;
- instalar una Action de terceros sin necesidad;
- tratar la key pública como contraseña de cuenta;
- guardar tokens privados junto al key file público;
- retries infinitos;
- usar timestamps falsos para forzar recrawl.

## 12. Coste / beneficio

Coste técnico: medio y acotado si se reutiliza el release manifest/registry.

Beneficio: alto para un sitio con fechas, eventos, convocatorias y hechos editoriales que pueden cambiar, porque reduce latencia de aviso a motores compatibles. No sustituye sitemap/crawling ni garantiza procesamiento.
